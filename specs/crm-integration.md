# Интеграция с CRM Яндекса: как работает по API

Рабочий документ по обмену с внутренней CRM (`crm.yandex-team.ru`). Здесь — что и когда
дёргаем, что передаём, что сохраняем у себя. Продуктовая часть (квалификация, канбан,
владение лидами) — в плане интеграции, здесь только механика API.

Термины: **аутрич-тул** — эта кодовая база, **CRM** — внутренняя CRM Яндекса, на которой
висит отчётность и дашборды.

---

## 1. Общая картина

Мы **пишем** в CRM реперные точки и **читаем** оттуда то, что двигают без нас. CRM ничего не
знает про нас и никуда не стучится: вебхуков наружу у неё нет, поэтому всё, что мы узнаём —
результат нашего же опроса.

```
аутрич-тул                                CRM
   │                                       │
   ├─ квалифицировали лида ──POST /issue──▶ создан тикет (Открыт)
   │                    └─2×execute──────▶ Валидирован | Дисквалификация+причина
   │                                       │
   ├─ менеджер двигает статус ─execute───▶ Сделан оффер / Согласие / Отказ+причина
   │                                       │
   ├─ забрал лида себе ───────PATCH──────▶ owner тикета
   │                                       │
   ◀── пуллер раз в час ─filtered+modified_on─┤ дельта: что двигали в CRM без нас
   ◀── открытие карточки ──/transitions──┤ какие кнопки легальны сейчас
```

**Авторизация.** Заголовок `Authorization: OAuth <CRM_TOKEN>`, база `https://crm.yandex-team.ru/api`.
При 401/403 — ответ вида `{"Message": "...", "Code": "..."}`.

**Ручной инструмент.** `scripts/crm.mjs` — CLI к тому же API: `api` (список ручек),
`schema <Имя>` (схема), любой метод напрямую. Мутации требуют `--yes`.

## 2. Генеральная таблица: событие → метод

| Событие в аутрич-туле | Метод | Что делаем |
|---|---|---|
| Вердикт квалификации вынесен | `POST /v0/issue` → 2× `POST /v0/issue/{id}/transition/execute` | создаём тикет и доводим до «Валидирован» либо «Дисквалификация» с причиной |
| Менеджер сменил статус канала в карточке | `POST /v0/issue/{id}/transition/execute` | один переход |
| Карточка переведена в колонку «Оффер» | `execute` по всем каналам админа | → `511` |
| Пиналка отстреляла, ответа нет | `execute` | → `708_792` / `708_791` |
| Менеджер забрал лида себе | `PATCH /v0/issue/{id}` | ставим `owner` |
| Нужен комментарий к исходу | `POST /v0/issue/{issueId}/comment` | отдельным вызовом, переходом текст не передаётся |
| Раз в час (пуллер) | `POST /v0/issue/filtered` с `modified_on` | подтягиваем то, что изменилось в CRM без нас |
| Открытие карточки лида | `GET /v0/issue/{id}` + `/transitions` | точная свежесть там, где смотрит человек |
| Синк графа воркфлоу (раз в сутки) | `filtered` + `transitions` по образцу на статус | обновляем справочник статусов и резолюций |

`GET /v0/issue/{id}/history` в этой таблице намеренно нет: это не механизм синка, а инструмент
разбора — см. §3.7.

Отправка опенера статус **не меняет** — холодное касание живёт внутри «Валидирован».

## 3. Детально по каждому вызову

### 3.1 Создание тикета

```http
POST /api/v0/issue
Content-Type: application/json

{
  "workflow_id": 41424,
  "queue_id": 7031220,
  "issue_type_id": 3,
  "category_id": 10444906,
  "name": "Привлечение блогеров: РСЯ 2_0",
  "text": "<карточка блогера, см. §5>",
  "owner": { "Login": "mikeshestakov" }
}
```

**Проверено записью в проде** (три тестовых тикета созданы и удалены):

- `owner` достаточно передать **одним `Login`**, без `Uid` — CRM резолвит сама и проставляет
  и `Uid`, и внутренний `owner_id`. Отдельного справочника сотрудников нам не нужно.
- Автором становится владелец токена — сейчас это сервисный робот `robot-outreach-tool`
  (`Uid 1120000001446178`, внутренний `created_by = 6347583`). Схема «создаёт робот, владелец
  — менеджер» получается сама собой, как и в нынешнем процессе.
- `category_id` принимается при создании (см. §3.2, без неё не закрыть исход).

Поля `state_id` в запросе **нет** — тикет всегда создаётся в дефолтном статусе воркфлоу
(`[2] Открыт`). Ответ — полный объект `Issue`, из него забираем `id`.

Дальше доводим до целевого статуса переходами. Создать тикет сразу в нужном статусе нельзя:
`state_id` в теле создания молча игнорируется (проверено — тикет всё равно «Открыт»).

**Граф переходов сервером не проверяется.** Из «Открыт» проходит `execute 507` и даже
`execute 511`, минуя промежуточные статусы. Мы этим **не пользуемся**: интерфейс такого не
показывает (он рисует только кнопки из `/transitions`), похоже на дыру в валидации, а не на
разрешённое поведение — починят, и интеграция встанет. Плюс пропуск «В работе» ломает их
счётчики воронки. Обратная сторона того же факта: сервер не поймает и наш баг, поэтому
легальность перехода проверяем у себя по зеркалу графа — это обязательное требование, а не
пожелание.

Идём честным путём:

```http
POST /api/v0/issue/{id}/transition/execute   { "state_id": "3" }     → В работе
POST /api/v0/issue/{id}/transition/execute   { "state_id": "507" }   → Валидирован
```

или при отбраковке — второй вызов с составным id:

```http
POST /api/v0/issue/{id}/transition/execute   { "state_id": "703_578" }  → Дисквалификация: подозрение на фрод
```

**Итого 3 вызова на лида, и они разнесены по реальным событиям, а не выпаливаются подряд:**

| Событие | Вызовы | Что видит CRM |
|---|---|---|
| Менеджер взял лида себе («Взять следующего») | `POST /issue` + `execute 3` | тикет в «В работе», владелец — менеджер |
| Вердикт квалификации | `execute 507` либо `execute 703_*` | Валидирован / Дисквалификация с причиной |

Тогда счётчик «В работе» в CRM показывает правду — сколько лидов разбирают прямо сейчас.
Подряд все три уходят только у автоотбракованных (нет контакта, мёртвый канал): там события
действительно совпали во времени.

### 3.2 Смена статуса

```http
POST /api/v0/issue/{id}/transition/execute
{ "state_id": "8_562" }
```

`state_id` — строка, и это может быть как простой id статуса (`"511"`), так и составной
`статус_резолюция` (`"8_562"` = Отказ, «не хочет добавлять бота»). Отдельного поля под
резолюцию нет: она уезжает вместе со статусом одним вызовом. Проверено записью: после
`{"state_id":"703_578"}` тикет получает `state_id=703, resolution_id=578`. Ответ — обновлённый
`Issue`, из него берём канонику и кладём в зеркало.

**Категория обязательна для исходов.** Движение вперёд (`В работу → Валидирован →
Сделан оффер`) проходит с пустой категорией, а любой переход с резолюцией — Дисквалификация,
Отказ — упирается в `400 INVALID_PARAMS: «У обращения должна быть заполнена категория»`.
Поэтому `category_id` проставляем сразу при создании; альтернатива — дослать `PATCH` перед
закрытием, но это лишний вызов на ровном месте.

Легальность перехода проверяет сервер. Мы у себя показываем только те кнопки, что пришли
в `crm_transitions`, но гонку это не отменяет: если статус успели двинуть в CRM, наш вызов
вернёт ошибку — обрабатываем как рассинхрон и перечитываем тикет.

### 3.3 Комментарий

```http
POST /api/v0/issue/{issueId}/comment
```

Нужен, только если менеджер сопровождает исход текстом. Переход комментарий не переносит —
`ExecuteIssueStateTransitionRequest` состоит ровно из одного поля `state_id`.

### 3.4 Владелец

```http
PATCH /api/v0/issue/{id}
{ "owner": { "Login": "...", "Uid": ... } }
```

Дёргаем, когда менеджер забрал лида себе (`contacts.assigned_to`). Владелец в CRM
проставляется на каждый тикет каналов этого админа.

Сейчас у 26 из 42 тикетов воркфлоу `owner_id = 0` — то есть «ничьи», лежат в общей куче.
Это подтверждает модель «взять следующего».

### 3.5 Пуллер: инкрементальный, раз в час

```http
POST /api/v0/issue/filtered
{
  "filter": { "workflow_id": [41424], "modified_on": ["2026-07-28T12:00:00+03:00"] },
  "fields": ["id", "state_id", "resolution_id", "owner_id", "modified_on"],
  "limit": 1000
}
```

`modified_on` работает как **нижняя граница «изменено начиная с»** — проверено на живых
данных: в воркфлоу 42 тикета, после 20.07 реально менялись 6, фильтр вернул ровно 6.
Передаём время прошлой успешной сверки — тянем только дельту.

**Раз в часа достаточно.** Пуллер нужен не для оперативности, а для дрейфа: когда менеджеры
переедут в аутрич-тул, руками в CRM будут двигать в основном хвост после «Согласие»
(регистрация, модерация, договор), а это работа других людей по карточкам, которые у нас уже
уехали в архив — там свежесть в минутах не нужна. Всё, что делаем мы сами, канонизируется
сразу: `transition/execute` возвращает обновлённый `Issue`. А там, где на данные смотрит
человек, свежесть даёт точечный запрос при открытии карточки, а не фоновый опрос.

**Только свои тикеты выбираем фильтром `created_by`** — по автору, а не по списку id.
Проверено: фильтр реально применяется (мусорное значение даёт 0, а не всю выборку), и поле
**отдаётся в ответе**, если запросить его в `fields`. У нынешней заливки `created_by = 68505`
(`robot-oobp-analytics`), у ручных тестовых тикетов — id живых людей.

```json
{ "filter": { "workflow_id": [41424],
              "created_by": [<id нашего сервисного аккаунта>],
              "modified_on": ["<время прошлой сверки>"] },
  "fields": ["id", "state_id", "resolution_id", "owner_id", "modified_on"],
  "limit": 1000 }
```

Свой id узнаём один раз, без помощи команды CRM: после создания первого тикета запросить
`filtered` по его `id` с `fields: ["created_by"]` — там и будет нужное число. Записать в
конфиг синка.

Почему не по списку `id`: он работает (проверил, массив из 1000 значений принимается), но на
5000 тикетов это 5 запросов с километровыми телами вместо одного, и список надо ещё
поддерживать. `created_by` даёт то же множество одним условием.

Тег для пометки «заведено аутричем» заводить не нужно, и он бы не помог: `tag_ids` на тикете
есть и ручки тегов есть, но **в `IssueFilteredListArgs` поля под теги нет** — отфильтровать
по нему нельзя.

**Два разных пространства id.** Фильтры (`created_by`, `modified_by`, `owner_id`) работают с
внутренним id CRM (`6299002`), а `owner` в создании и `author` в ответе — с яндексовым
`Uid` (`1120000001358696`). Это разные числа для одного человека, и перепутать их легко:
проверено — фильтр по `Uid` молча возвращает ноль.

Ограничения и грабли:

- **`limit` максимум 1000**, больше — `400 INVALID_PARAMS`.
- **Offset'а нет** — страничного курсора в контракте не предусмотрено. Инкрементальное окно по
  `modified_on` снимает проблему: за час изменений заведомо меньше тысячи. Для разовой полной
  вычитки большой базы придётся резать окнами по датам.
- **Невалидный фильтр молча игнорируется.** `modified_on: [">2026-07-20"]` вернул все 42 —
  операторный синтаксис не поддерживается, и вместо ошибки фильтр просто отключился. Ошибка в
  формате даты превратит инкрементальный синк в полный, и заметить это можно только по объёму.
  Формат даты валидировать у себя, а размер ответа логировать.
- **Не все поля отдаются.** `priority_id` и `communication_type_id`, запрошенные через
  `fields`, вернулись пустыми, хотя в полном `GET /v0/issue/{id}` они есть. Для пуллера
  хватает `state_id`/`resolution_id`/`owner_id`; остальное — только полным GET.
- В ответе поле называется **`modified_On`** (с заглавной O), хотя в фильтре — `modified_on`.

### 3.6 Кнопки для карточки

```http
GET /api/v0/issue/{id}/transitions
```

```json
{ "current":     { "id": "507", "name": "Валидирован", "resolution_name": null },
  "transitions": [ { "id": "511",   "name": "Сделан оффер", "resolution_name": null },
                   { "id": "708_791", "name": "Нет связи", "resolution_name": "Перестал отвечать" } ] }
```

Дёргаем при открытии карточки лида — чтобы кнопки были не из вчерашнего снимка. Батча нет,
только по одному тикету, поэтому на доску это не вешаем.

### 3.7 История

```http
GET /api/v0/issue/{id}/history
```

Строка вида:

```json
{"Type":"Modify","Date":"27.07.2026 17:22:11","Author":"Шестаков Михаил",
 "Fields":[{"Name":"Статус","Old":["В работе"],"New":["Валидирован"],
            "FieldChange":{"name":"State","old":"3","new":"507"}}]}
```

Штатно не вызывается. Нужна в двух случаях: когда зеркало разошлось с CRM и надо понять, кто
двинул статус — наш воркер или человек руками (в ответе есть `Author`), и при восстановлении
графа, потому что переходы, которых нет ни в одном живом тикете, видны только здесь.

## 4. Что храним у себя

### 4.1 Справочник статусов и резолюций — храним

Таблица `crm_workflows`, поле `graph jsonb`. Обновляется раз в сутки обходом
`filtered` → `transitions` по одному образцу на каждый встреченный статус.

```json
{ "states": [
    { "stateId": 3, "name": "В работе", "buttons": [
        { "label": "Валидирован", "targetStateId": 507, "transitionId": "507", "resolutions": [] },
        { "label": "Дисквалификация", "targetStateId": 703, "transitionId": null,
          "resolutions": [ { "transitionId": "703_775", "name": "Не размещает рекламу" },
                           { "transitionId": "703_776", "name": "Нет в РКН" } ] } ] } ] }
```

Зачем храним, а не дёргаем каждый раз: выпадашки причин нужны в списке квалификации на сотне
строк сразу, а `transitions` работает по одному тикету. Плюс это защищает от того, что
названия причин поменяют на стороне CRM — мы увидим диff, а не тихую подмену.

**Резолюции привязаны к статусу-исходу, а не к ребру.** Проверено: набор «Отказ ▾ 14»
идентичен из «Валидирован», «Сделан оффер» и «Согласие». Поэтому в графе они лежат один раз.

### 4.2 Состояние конкретного тикета — храним снимком

На `project_items` (одно размещение = один канал = один тикет):

| Поле | Что лежит | Откуда |
|---|---|---|
| `crm_issue_id` | id тикета | ответ `POST /v0/issue` |
| `crm_state_id` | `507` | `Issue.state_id` |
| `crm_state_name` | `«Валидирован»` | `Issue.state.name` |
| `crm_resolution_id` | `578` или null | `Issue.resolution_id` |
| `crm_resolution_name` | `«Подозрение на фрод»` | `transitions[].resolution_name` |
| `crm_transitions` | кнопки, легальные сейчас | `GET /transitions` |
| `crm_synced_at` | когда сверяли | наш таймстамп |
| `crm_sync_error` | текст последней ошибки | наш |

Имена (`state_name`, `resolution_name`) дублируют справочник намеренно: это **снимок на момент
события**. Если в CRM переименуют причину, в истории лида останется та формулировка, под
которой решение принимали. Источник истины для логики — всегда числовой id.

### 4.3 Вердикт квалификации

`project_items.qual_reason` хранит **id перехода CRM** (`"703_578"`), а не наш собственный код.
Своего словаря причин не заводим вообще: причины отбраковки — это причины CRM, и любое
расхождение здесь сразу превратится в расхождение отчётности.

### 4.4 Очередь

`crm_sync_jobs` — исходящие вызовы. Пишется в одной транзакции с локальным изменением, иначе
при падении между «сохранили у себя» и «отправили» получим тихое расхождение. Поля: тип
(`create` / `transition`), целевой `transition_id`, попытки, `run_after`, последняя ошибка.

Идемпотентность: уникальный индекс на `project_items.crm_issue_id`. Ретрай задачи, успевшей
создать тикет до таймаута, не должен породить дубль.

## 5. Формат `text` и ссылки

Отдельного поля под URL в `Issue` нет (`ya_messenger_widget_url` — внутреннее поле CRM, не
наше). Ссылки кладём в `text`, дописывая к их же формату. Как выглядит существующий тикет:

```
Дата заливки: 2026-07-02
Название канала: НЕБОЖЕНА
Кол-во подписчиков: 129810
Тип монетизации: CPV, CPC
Особые отметки:
Ссылка: https://max.ru/nebozhena
Chat_id: -68189873542520
Категория канала: Юмор и развлечения
Телефон:
Почта партнера:
Контакт в ТГ/Макс:
Тип блогера: regular
Тип площадки: MAX
Resolution: new
```

Формат воспроизводим один в один (иначе сломаем тех, кто парсит эти тикеты глазами или
скриптом) и дописываем в конец:

```
Лид в аутрич-туле: https://<WEB_ORIGIN>/w/{wsId}/projects/{projectId}/leads?lead={itemId}
Переписка (без доступа в аутрич): https://<WEB_ORIGIN>/share/conv/{token}
```

Первая — для тех, у кого есть доступ. Вторая — постоянная ссылка на диалог из
`conversation_shares` (бессрочная по замыслу, гасится только `revoked_at`). Обратно: на
странице шаренной переписки показываем ссылку на тикет CRM.

**`Chat_id` — наш ключ матчинга.** Связать существующие 42 тикета с нашими размещениями можно
только через него или через `Ссылка:` — отдельного поля под внешний id в `Issue` нет,
`gallifrey_uuid` пуст.

## 6. Что известно про поля создания (словарей в API нет)

Проверено выборкой по живым данным, потому что `GET /v0/dictionary` этих справочников
не отдаёт (в нём 22 словаря: бренды, отрасли, тиры, роли, `communicationType` и продуктовые —
типов тикета, очередей, приоритетов и категорий среди них нет).

| Поле | Что стоит в живых тикетах | Комментарий |
|---|---|---|
| `issue_type_id` | `3` у всех 42 наших и у всех 1000 просмотренных тикетов CRM | «Тикет». Других типов в выборке не встретилось вообще |
| `queue_id` | `7031220` у всех 42 | очередь блогерского воркфлоу |
| `workflow_id` | `41424` | «РСЯ 2.0» |
| `priority_id` | `8` (в полном GET; в `filtered` не отдаётся) | значение одно на всех, смысл неизвестен |
| `category_id` | `0` у 32, `10444906` у 7, `208529537` у 3 | **обязательна для исходов** — без неё не пройдёт ни Дисквалификация, ни Отказ. Проставляем при создании. Это ветка продуктовой таксономии саппорта («РСЯ и Adfox → Продукты → РСЯ для блогеров → …»); берём `10444906` — значение с роботной заливки реальных блогерских тикетов. Смысла в ней для нас нет, но без неё воронка не закрывается |
| `communication_type_id` | `1` (Mail) у проверенного тикета | словарь есть: Mail 1, InCall 2, OutCall 3, Chat 4, InternalChat 5, WhatsApp 6/7, Viber 8, TelegramBot 9, **Max 11**, не задан 0 |
| `business_unit_id`, `ya_service_id` | пусто у всех | не заполняем |
| `owner` | `{Login, Uid}`; `owner_id = 0` у 26 из 42 | больше половины тикетов ничьи |

Swagger не помечает **ни одно** поле создания как обязательное — что реально required,
из контракта не выводится.

## 7. Решённое и оставшиеся вопросы

### Закрыто проверкой в бою

| Было непонятно | Ответ |
|---|---|
| Права токена на запись | Есть. Создание, переходы, `PATCH`, комментарий, удаление — всё отработало |
| `owner`: нужен ли `Uid` | Нет, достаточно `Login`. Справочник сотрудников не нужен |
| Кто автор тикета | Владелец токена — робот `robot-outreach-tool`. Схема «создаёт робот, владелец менеджер» работает из коробки |
| Наш `created_by` для фильтра | `6347583` |
| Составной `state_id` с резолюцией | Работает: `"703_578"` → `state=703, resolution=578` |
| Обязательные поля создания | `workflow_id`, `queue_id`, `issue_type_id`, `name`. Плюс `category_id`, иначе не закрыть исход |
| Удаление тестовых данных | `DELETE /v0/issue/{id}` → `{"Success":true}`, дальше GET отдаёт «Выбранная задача удалена» |

### Менеджеры: как узнать, кто есть, и как передать ответственного

Для передачи ответственного справочник **не нужен**: `owner: {Login}` резолвится самой CRM.
Логин — свойство нашего пользователя (`users.crm_login`), а не то, что ищется в CRM.
Цепочка: «взять себе» → `contacts.assigned_to` → воркер берёт `users.crm_login` →
`PATCH /v0/issue/{id}` с `{owner:{Login}}` по всем каналам админа.

Если роспись всё же нужна, есть три источника, и запрет на `/v0/manager/bylogin` (403) ни
одному не мешает:

1. **Из тикетов.** `owner_id` приходит в `filtered`, а полный `GET /v0/issue/{id}` отдаёт
   `owner: {Login, Uid}` — так связываются все три пространства id. Действующий состав
   воркфлоу 41424 на 28.07.2026:

   ```
   6209580 akudas        296780 lissimji       6243751 tanyatikhonov   6299002 mikeshestakov
   151659  trutova-ks    242015 pavelreshetov  6246636 luiza777        121341  chetmari
   ```

2. **`GET /internal/bpms-tasks/get-available-manager?queueId=7031220`** → `{manager_id,
   manager_login}`. Собственный распределитель CRM: отвечает, кому сейчас можно назначить.
   Знает роспись очереди целиком — вернул `alenkayaalina`, которой нет среди владельцев
   тикетов. Без `queueId` отдаёт 404. **Готовая механика на случай, если однажды захотим
   автораспределение вместо ручного «взять следующего».**
3. **`GET /v0/user/user-status/{внутренний_id}`** — статус коллеги (доступен / оффлайн).
   Пригодится, чтобы не назначать на того, кто не на линии.

### Решено без вопросов к команде

- **Тестового контура нет** — работаем сразу в проде, как и все. Тестовые тикеты создаём с
  явным именем и удаляем за собой.
- **`issue_type_id = 3`**, **`priority_id = 8`** — везде одно и то же, берём как есть.
- **`category_id = 10444906`** — обязательна для исходов, ставим при создании.
- **`communication_type_id`** — хардкодим из словаря по площадке: `Max (11)`, `TelegramBot (9)`.
  Словарь получен, менять его незачем.
- **Лимитов API нет** (внутренняя система), пакетного создания тоже нет. Тикет создаётся не
  пачкой, а по одному в момент валидации лида — троттлинг не нужен.
- **Матчинг старых тикетов не нужен**: обрабатываем только то, что заведено через аутрич-тул,
  фильтр `created_by` это и обеспечивает.

### Осталось уточнить

1. **Постраничная выборка.** Офсета нет и подобрать не вышло: `offset`, `skip`, `page`, `from`,
   `start` — все шесть вариантов, и на верхнем уровне, и внутри `filter`, вернули ту же первую
   страницу. Штатный синк закрывается окном по `modified_on`, но для разовой вычитки базы
   больше 1000 тикетов способа нет. Спросить: как правильно, и каков точный формат
   `modified_on` / `created_on` — один элемент работает как «начиная с», а что означает второй?
2. **Статус «Отложить».** Остальной граф достроен обходом живого тикета (см. плановый
   документ), но «Отложить» не предложен ни в одном из десяти состояний. Откуда он доступен —
   или это действие интерфейса, а не переход?
3. **Два «Заключил договор».** Кнопка ведёт в `707`, а тикет оказывается в `774` с тем же
   названием; в истории старых тикетов фигурирует `707`. Похоже, `707` — legacy. Уточнить,
   какой из них актуален, чтобы зеркало не считало их разными исходами.
4. **Увидят ли дашборды наши изменения сами?** Формулировка для команды CRM: «мы меняем
   статусы тикетов через ваш же API — нужно ли дополнительно уведомлять систему, чтобы отчёты
   и поиск подхватили изменения, или всё обновляется само?»

   Откуда вопрос: в API есть ручка `POST /v0/entity/updated`, которая принимает список «такая-то
   запись такой-то сущности создана/изменена/удалена». Похоже, она для внешних систем, которые
   владеют данными **вне** CRM и должны сообщать ей о правках. Наш случай другой — мы пишем
   в саму CRM, так что она о наших изменениях знает по определению. Но если между базой и
   дашбордами есть промежуточный слой (индекс, витрина), который обновляется по такому
   уведомлению, мы про него не знаем и молча получим отставшую отчётность.
   Пока исходим из того, что дёргать не нужно.

Отдельной причины «сообщение не прочитано» в словаре «Нет связи» заводить **не нужно**:
`708_792` «не отвечает на первое сообщение» описывает наблюдаемый факт и покрывает оба случая —
и «увидел, промолчал», и «не открывал». Различие read / unread остаётся нашим внутренним и
влияет не на выбор резолюции, а на то, **закрываем ли мы исход вообще** (см. §4 плана,
этап 6): непрочитанное — сигнал, что пишем не туда, и лид уходит в резолвер контакта, а не
в «Нет связи».

## 8. Проверка

- `node scripts/crm.mjs GET /v0/issue/{id}/transitions` — сверить справочник графа с живым API.
